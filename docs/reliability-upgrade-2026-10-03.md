# 简报与商机可靠性更新（2026-10-03）

这一轮修的是“结论不可靠”的问题，没有新增栏目，也没有改动微信接入。首次获取 key 的状态不变，见[接入支持流程](access-support.md)。

## 修了什么

| 问题 | 之前 | 现在 |
| --- | --- | --- |
| 长时间范围的简报漏掉最新消息 | 窗口超过 12,000 条时只读最早的 12,000 条，没有任何提示 | 上限提高到 60,000 条；超出时保留最新的消息，并在“覆盖”一行写明总数、已读数和缺口 |
| 合作前问发票被当成待结算 | 消息里出现“发票、付款”就判为 `已发布待结算` | 询问能否开票、怎么付款、账期、定金等归到 `待确认报价/排期`；催款、已开票、已打款才算结算 |
| 机器猜的阶段自动变成正式机会 | 每次打开数据库，阶段不是“新线索”的候选都会被升级 | 只有人工操作过的记录才升级；旧数据库升级时的一次性迁移保留 |
| 等待中的商机从今日行动里消失 | 可以设为 `waiting` 而不给日期，之后不再出现 | 设为 `waiting` 必须带有效日期；已有的无日期记录排在今日行动末尾并标出 |
| 回复草稿编造上下文 | 第一次询价也回“前面是单条价” | 只有本人在该聊天里报过单条价，草稿才会这么说；否则先问需求，或只说确认后回复 |
| 新增专题 Markdown 没进 HTML | 没有映射的文件被直接丢掉，没有提示 | 用 `report_manifest.json` 指定分区；未进入 HTML 的文件在渲染结束时列出 |

另外，多风格 HTML（信号雷达、编辑简报、台账，各有跟随系统、亮色、暗色）和群聊分页未读完的覆盖提示，这次一并进入公开仓库。

## 怎么验证的

- 2026-09-28 审计中用虚构数据复现的 8 个场景，7 个不再复现，并已写成回归测试。
- Hub 测试 157 项通过，发布包再跑一遍 157 项通过；Reader 155 项通过，其中 2 项 Windows 原生测试在 Mac 上跳过。
- 结算判断用三组共 56 条虚构消息对照了 JEV（`jev-1.13.0`）的分类。改动前规则对 23 条，把 16 条非结算消息误判为待结算；改动后对 54 条，误判 1 条。这三组后来都参与过调规则。真正没见过的那一组 16 条，规则第一次跑只对了 12 条，所以真实聊天里的准确率会低于 54/56。
- 发给 JEV 的只有作者自拟的虚构消息。真实聊天、联系人和金额没有离开本机。

## 还没解决

- 同一个对接人的不同项目仍会合并成一条商机，金额和阶段会混在一起。拆分需要改存储结构并先预览历史数据，留到下一轮。
- 结算判断仍是关键词规则，说法一换就可能漏判或误判。Agent 写报告前要回看原消息，规则见 Skill 的 `references/signal-rules.md`。
- 没有覆盖 Windows 和失败 Mac 上的首次获取；候选获取补丁仍未作为默认路线。

## 升级已有安装

让本地 Agent 更新代码后跑一次 Hub 测试即可，Profile、数据库和访问材料不用动。升级后如果 `opportunity-update --status waiting` 报“必须有跟进日期”，补上 `--follow-up YYYY-MM-DD` 再执行。
