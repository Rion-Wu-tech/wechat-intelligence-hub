# 产品需求文档 (PRD)：微信智能瘦身与无损归档系统 (WeChat Slim)

---

## 1. 文档概述与定位

### 1.1 产品名称与定位
* **产品名称**：WeChat Slim（微信智能瘦身与无损归档引擎）
* **产品定位**：面向 Mac / PC 用户的**高安全、带文件感知**的微信存储管理、极速瘦身与无损归档系统。
* **核心价值主张（Value Proposition）**：
  > **“一条文字都不丢，家庭客户永不删；多端文件去重复，五十个 G 存外置。”**

### 1.2 核心痛点与背景
1. **磁盘空间危机**：大量 Mac/PC 用户微信长期占用 50GB～150GB 甚至更多硬盘空间，严重拖慢系统并频繁弹出磁盘告急。
2. **实测数据证实**：经实际 Mac 微信存储深度分析，**核心文字与会话数据库仅占 170MB（< 3.5%）**，而附件、下载文件和视频占了 **96.5% 以上**！
3. **误删恐惧症**：用户不敢直接清理，因为绝大多数清理工具是“盲删”，无法区分“水群沙雕视频”与“家人温馨录像”、“客户合同 PDF”。
4. **沉淀与归档缺失**：用户并不想把文件直接抹除，而是希望腾出电脑昂贵内置固态硬盘的同时，将回忆和重要资料安全转存到外接硬盘或 NAS。

## 3. 用户画像与典型用例

### 3.1 典型画像
1. **MacBook 存储焦虑型白领 / 程序员**：
   * 设备：MacBook Air/Pro（256G / 512G SSD），剩余空间不足 10G；
   * 诉求：希望能立刻安全释放 40G+ 空间，保证正常工作，不想花大几千换电脑。
2. **多群聊商务 / 销售 / 独立顾问**：
   * 痛点：有几十个工作群、客户群，每天被大量重度文件轰炸；
   * 诉求：群里别人发的无关大文件随便删，但甲方发过来的合同、报价表绝对不能碰。
3. **家庭记录守护者**：
   * 痛点：想清理微信空间，但里面有老婆孩子几年来发的照片和视频，生怕手抖误删。

## 4. 存储结构实测与逆向分析（Mac 平台）

### 4.1 微信 4.0+ 最新架构（当前主流）
路径：`~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/<account_id>/`
* `msg/attach/`：聊天中收到的图片与媒体附件（通常占 50%+ 空间）；
* `msg/video/`：视频文件目录（占 20%+ 空间）；
* `msg/file/`：接收的 Word/Excel/PDF/安装包（占 20%+ 空间）；
* `cache/` 与 `temp/`：缩略图、临时加载项（直接可安全清理）；
* `db_storage/`：**核心 SQLite 数据库与文字消息（绝对保护，禁止删除）**。

### 4.2 微信 3.x 传统架构
路径：`~/Library/Containers/com.tencent.xinWeChat/Data/Library/Application Support/com.tencent.xinWeChat/<version>/<account_md5>/`
* `Message/MessageTemp/`：聊天多媒体附件；
* `HardLinks/`：群聊硬链接。

## 6. 极简 CLI (MVP) 详细规范与命令设计

为了保证以最快速度落地、最低风险运行，第一期交付**极简终端 CLI（`wechat_slim.py`）**。

### 6.1 命令结构与参数
```bash
# 1. 默认无参运行：启动交互式向导（推荐）
python3 wechat_slim.py

# 2. 纯扫描分析：只看不动，输出当前磁盘占用与可瘦身潜力
python3 wechat_slim.py scan

# 3. 极速一键瘦身（模拟演练 / Dry-Run，不删任何文件）
python3 wechat_slim.py clean --dry-run

# 4. 指定规则瘦身（移动到废纸篓，安全可逆）
python3 wechat_slim.py clean --days 90 --min-size 20MB --types video,file

# 5. 无损转存到外接移动硬盘 / NAS（安全归档模式）
python3 wechat_slim.py clean --days 180 --archive-to "/Volumes/MyPassport/WeChat_Archive"

# 6. 多群转发文件秒级查重与 APFS 硬链接去重 (零风险，聊天窗口文件正常打开)
python3 wechat_slim.py dedup --action hardlink

# 7. 启动本地现代化图形大盘 (WebUI，零依赖开箱即用)
python3 wechat_slim.py web --port 8080
```

### 6.3 核心安全规范
1. **默认使用废纸篓（macOS Trash）**：除非用户显式要求永久抹除，所有清理动作均调用原生 API 移入废纸篓，用户随时可在访达中一键“放回原处”。
2. **演练机制（Dry-Run）**：支持 `--dry-run` 标志，在真正移动任何字节前，打印精确清单与将释放的字节数。
3. **数据库隔离保护**：任何清理规则强制排除 `*.db`、`*.db-*`、`db_storage` 目录，确保聊天文字和索引 100% 不受影响。

## 8. 已知限制与技术边界（重要 · 必须如实告知用户）

> 本节记录经**实机验证**的真实能力边界。对外宣传或撰写文档时，不得超出本节范围承诺。

### 8.1 微信 4.0 数据库是加密的 —— 联系人维度目前物理上不可实现

* 实测结论：`db_storage/contact/contact.db`、`db_storage/message/*.db` 均为 **WCDB / SQLCipher 加密库**，
  直接用 sqlite3 打开会抛 `DatabaseError: file is not a database`。
* 推论：在未取得解密密钥的前提下，**无法**得知"这个文件是谁发的""属于哪个会话"。
* 因此第 2 节竞品矩阵中的"聊天上下文认知 / 按联系人防删"在**当前阶段无法兑现**，
  不应作为已交付能力对外宣传。

### 8.2 白名单的真实可用维度（已实测）

| 维度 | 是否可用 | 说明 |
| :--- | :---: | :--- |
| 文件名关键词 | ✅ **可用** | `msg/file/` 保留原始文件名（实测：`嘉华.pdf`、`委托书（蔡俊松）.docx`、`圣嘉模具xin(2).xls`）。配置"合同/报价/对账单"等关键词即可精准保护。 |
| 精确路径段 (wxid) | ⚠️ 仅兼容 | 仅当目录名**完全等于**该 wxid 时命中。微信 4.0 文件路径不含联系人 wxid，故此维度实际很少生效。 |
| 按发送者 / 群聊 | ❌ **不可用** | 依赖解密数据库，见 8.1。 |
| 哈希命名的媒体 | ❌ 不适用 | `msg/video/`、`msg/attach/` 为 32 位哈希命名，无语义信息，关键词维度对其无效，只能按时间 / 大小 / 类型处理。 |

### 8.3 已修复的历史缺陷：白名单对整个账号的致命误判

* **缺陷**：匹配逻辑曾用 `r_wxid in path_str` 对**完整绝对路径做子串匹配**。
  而微信 4.0 账号根目录本身就形如 `<wxid>_<序号>`（如 `xwechat_files/wxid_kdm0jksur2yh12_6804`），
  导致任意 wxid 规则都会命中该账号下 **100% 的文件**。
* **后果**：报告显示"已保护 5.4GB"纯属假象 —— 白名单要么保护一切（工具什么都不敢删），
  要么对真实联系人完全失效。
* **实测复现**：本机 15,458 个文件，单条规则即全部误判为"受保护"。
* **修复**：wxid 仅允许"精确路径段"匹配，并补充 5 项安全回归测试（commit `87cff06`）。
  修复后同场景命中数为 **0**（真实）；关键词规则则精准命中 17 个业务文件 / 42.6 MB。

### 8.4 让"联系人级防删"成为现实的唯一路径（Phase 4 候选）

* 复用本仓库已有的 `projects/rion-wechat-reader/`（SQLCipher + Zstandard 解密读取器），
  在用户提供解密密钥的前提下，构建 **文件 → 发送者/会话** 映射索引；
* 将索引注入 `WhiteListManager`，即可实现真正的"家人 / 重点客户文件永不误删"；
* 未配置密钥时应**优雅降级**到 8.2 的真实可用维度，并明确提示用户当前保护范围。
